# Frozen Message Queues and Background Workers contract

Prepared independently before seeing any lesson prose, diagrams, source reports or sibling contracts. Read only evals/lessons/README.md, rubric.json and backlog.md in /tmp/system-canvas-card-evals. Eight cards teach one connected progression: acceptance versus completion; producer/broker/worker handoff; acknowledgement and duplicate-safe effects; bounded failure handling; dependency ordering; sustainable capacity; work queues versus retained logs; choosing the request boundary. An author should use one evolving operation across the teaching, while the assessment scenarios intentionally transfer to other operations.

The six whole-stack questions explicitly request every grading criterion. Eight prefix questions require only the target card and preceding material. Every card has one objective and earlier-card prerequisites. The final card integrates earlier mechanisms instead of introducing another technology. A simple structural check verified card count, question count, slide order and prerequisite direction; this is not a content or UI gate.

Scope decisions:

- Relational transaction atomicity and uniqueness are declared prerequisites so the idempotency card can teach a concrete atomic duplicate-safe database effect without an implementation detour. Explain why separately checking an ID and applying a write leaves a gap. An external side effect is not magically made atomic by a database marker; do not imply otherwise. External-provider idempotency APIs may be a brief optional example, never an undeclared assessment requirement.
- Distinguish broker publication acceptance from worker processing acknowledgement. Condition acceptance and durability claims on the selected broker configuration. No assessment asks for an outbox implementation, distributed transaction, publisher crash recovery protocol or universal durable-delivery guarantee.
- Define retry, backoff, poison message, dead-letter destination, partition, group and offset on first use. A dead-letter destination provides isolation and investigation, not automatic repair. Finite budgets and deliberate replay are enough; no prescribed exponential formula or jitter algorithm is required.
- Ordering asks for a rule that serializes dependent effects for one entity, including retry interference. It does not require Kafka-specific assignment APIs, FIFO service configuration, sequence reconciliation or an advanced coordination protocol. An unresolved earlier dependency may block that entity; avoid claiming dead-lettering automatically makes later dependent work safe.
- Capacity questions give rates and saturation as explicit facts. They require basic arithmetic, oldest-job-age interpretation and bounded admissions, not queueing theory or a particular autoscaler.
- A work-queue model distributes logical jobs among competing workers; this does not imply zero duplicates or that brokers cannot support fan-out through additional queues. A retained log keeps records according to retention and gives separate groups independent progress. Product-specific retention exceptions, ordering guarantees, offset policies and exactly-once features belong to later lessons. Shared foundations must not imply every product has identical semantics.
- Log ordering is scoped, typically per partition. Consumer progress is not an atomic guarantee for an arbitrary external effect. Replay depends on retained data being available and does not by itself undo or deduplicate earlier effects.
- The diagram file is src/learn/QueueDiagram.tsx. Diagrams should distinguish acceptance/completion and publication/processing acknowledgements, and visually distinguish work distribution from independently positioned log groups. Draw no universal delivery, durability or global-order guarantee.
