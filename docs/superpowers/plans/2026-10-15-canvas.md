# Distributed Systems Canvas Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking. Obtain the user's execution-method choice before implementation.

**Goal:** Deliver the approved local-first architecture canvas with reliable editing, containers, saved diagrams, and portable files.

**Architecture:** A React Flow editor renders a framework-independent diagram model. Pure editing operations feed a single history reducer; a separate IndexedDB adapter handles durable records and revision conflicts. Catalog presets and starter documents are data, not application logic.

**Tech Stack:** React, TypeScript, Vite, @xyflow/react, ordinary CSS, lucide-react, idb; Vitest, fake-indexeddb, React Testing Library, and Playwright for validation. Use compatible stable releases and commit the npm lockfile.

**Spec:** `docs/superpowers/specs/2026-10-15-canvas-design.md`

## Global Constraints

- Use the existing isolated checkout at `/workspace/distributed-sim`; no additional worktree is needed.
- No backend or external credentials are needed.
- Containers cannot be nested in this release.
- Technology choices change presentation only; they do not introduce capacity, protocol, or deployment assumptions.
- History is per open diagram, bounded to 100 entries, and does not survive reload.
- Cap imports at 5 MiB, 500 elements, and 1,000 connections; explain exceeded limits.
- Import always creates a new diagram and never overwrites an existing one.
- Never claim success before the write completes.
- Do not show inactive controls for deferred features, including simulation, analysis, learning, accounts, and hand-drawn mode.
- Icons must not require runtime third-party requests. Preserve the uploaded prototype unchanged.

## Review Focus

- Rapid edits while a save is in flight must not let an older completion mark newer changes as saved (Task 6).
- Another tab deleting a record must not let an old tab silently recreate it (Task 4).
- A member selected with its container must move or duplicate exactly once (Tasks 2 and 5).
- Imported HTML-like text and extreme finite coordinates must remain inert and bounded (Tasks 3 and 7).
- Keyboard shortcuts inside inputs, textareas, and contenteditable elements must preserve normal editing (Task 5).

Shared model decisions (implementation defaults within the approved spec):

```ts
type Point = { x: number; y: number };
type Viewport = Point & { zoom: number };
type ElementKind = 'component' | 'sticky' | 'text' | 'container';
type DiagramNode = {
  id: string; kind: ElementKind; position: Point;
  width: number; height: number; parentId?: string;
  name: string; notes: string; description: string;
  componentType?: string; category?: string; technology?: string;
  color?: string;
};
type DiagramEdge = {
  id: string; source: string; target: string;
  sourceHandle: string; targetHandle: string;
  label: string; direction: 'one-way' | 'both';
};
type Diagram = {
  schemaVersion: 1; id: string; name: string;
  createdAt: string; updatedAt: string;
  nodes: DiagramNode[]; edges: DiagramEdge[]; viewport: Viewport;
};
type StoredDiagram = { document: Diagram; revision: number };
type Selection = { nodeIds: string[]; edgeIds: string[] };
```

Positions are relative to `parentId` when present; otherwise world coordinates. Initial component dimensions are 200×88, sticky 240×160, text 240×80, container 640×400. Container padding is 24, duplication offset is (32,32), autosave debounce is 400 ms. Use `crypto.randomUUID()` for new IDs. Four stable component handles (`top`, `right`, `bottom`, `left`) permit flexible connections. Initial viewport is `{x:0,y:0,zoom:1}`; zoom range is 0.2–2. Names are limited to 200 characters; technology and labels to 200; descriptions and notes to 10,000. Document these limits in import errors.
